# Autonomous product-studio runtime

This is a real, local Windows supervisor, not a claim that a chat keeps working after it ends. It requires this computer awake, the current user logged in, network access, and valid existing ChatGPT authentication/usage. It cannot guarantee uninterrupted service or sales. It never starts paid API fallback.

The scheduler checks cheaply every 30 minutes and at logon. Model work is limited to two daily slots, **09:00 and 17:00 Europe/Bucharest**, with at most two model-start attempts per local day. Windows timezone `GTB Standard Time` supplies the daylight-saving rules; this is not a fixed UTC offset. An awake PC starts on the next scheduler check in the eligible window. When waking late, only the latest due slot can run; earlier missed slots are skipped, with no catch-up burst. The private `schedule-ledger.json` reserves a slot atomically under the exclusive cycle lock before launching the model. A failed launch, usage rejection or interrupted cycle consumes its slot. A missing or malformed ledger fails closed. Explicit resume cannot bypass the slots or daily cap. These limits bound starts and runtime, not an exact token or monetary amount.

One cycle can work for at most 25 minutes, with an OS-held exclusive file lock and a 10-second heartbeat. Scheduler `IgnoreNew` is a second overlap guard. A retained `running` status with no lock owner becomes an explicit interrupted fault; its old heartbeat and unfinished work remain preserved. Auth, quota, exit, verification, dirty-tree and malformed-result failures also latch closed. Reporting succeeds through verified live publication or a committed, freshly timestamped static fallback; missing credentials alone do not block useful product work. Failed cycles never retry until inspected and explicitly resumed. Owner-blocked cycles cheaply poll the existing HQ helper without invoking a model; a changed response for a current decision or restored reporting credentials permits work in the next eligible slot. Unchanged/unrelated decisions do not launch work. Fault/paused states still require deliberate resume.

Work happens only in the retained `studio/autonomous` Git worktree under ignored `runtime/worktree`. Main is not automatically merged or pushed. The runtime uses configured model settings without overrides, `workspace-write` sandbox and `never` approval; sandbox failures are recorded, never bypassed. Native CLI `--worktree` was evaluated but requires a disabled experimental feature and cannot combine with `--ephemeral`; ordinary Git worktrees provide stable isolation instead.

The first real cycle (`20260913T215752Z`) proved that the default workspace sandbox blocked npm registry requests: `npm.cmd view next@16.3.5` failed with `EACCES` on `https://registry.npmjs.org/next`. The runner now supplies the documented invocation-only `-c sandbox_workspace_write.network_access=true` for the authorized package/research work. This enables outbound networking; it does not change filesystem roots, Git permissions, global configuration, or production/outreach/spending authorization. It is not a domain allowlist. See the [official configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference). On Windows, agent commands use `npm.cmd` to avoid the blocked PowerShell npm.ps1 shim; machine execution policy remains unchanged. The configuration change needs a separately observed subsequent cycle; it does not retroactively make the failed cycle successful.

The model prepares unstaged files and scoped checks within 15 minutes. It never stages or commits shared Git metadata. The supervisor reserves the rest of the 25-minute cycle for independent workspace typechecks, all hermetic workspace tests with two workers, lint and web production build. Only after every check passes does it stage explicitly allowed paths and commit on `studio/autonomous`, with hooks/signing disabled for that command so no external hook can publish. Source main refs remain untouched. Failed checks preserve unstaged work for review. Product source/public/docs paths and the existing dependency manifests/root lock are supported; runtime/control/auth files and operating instructions are excluded. Manifest edits must preserve scripts/workspace roots and trigger independent `npm ci --ignore-scripts` before checks. Any newly required lifecycle scripts or other paths need separate review, not a sandbox bypass. The exact allowed paths are in `cycle-prompt.md` and enforced by `supervisor.mjs`.

The operating contract and authorized HQ helper must be committed first. Install from the repository root:

```powershell
powershell -NoProfile -File .agents/product-studio/test-runner.ps1
powershell -NoProfile -File .agents/product-studio/test-schedule.ps1
node --test .agents/product-studio/reporting.test.mjs
node --test .agents/product-studio/supervisor.test.mjs
powershell -NoProfile -File .agents/product-studio/install.ps1 -RegisterTask
```

Installation creates a disabled schedule in a logically paused state; it does not launch a cycle. The installer refuses to replace any existing runtime history. For an existing disabled task, upgrade the schedule and normalize interrupted status without contacting providers, starting a model or enabling the task:

```powershell
powershell -NoProfile -File .agents/product-studio/configure-schedule.ps1
```

The upgrade preserves exact previous config/status/ledger bytes and task XML in ignored runtime backups. It aligns cheap checks to the hour/half-hour while leaving the task disabled. It does not reset a configured ledger or discard either worktree. If legacy work already started on the current local day, reconcile that day's starts before migrating; the upgrader refuses an unknown budget. The runtime config's schedule is `{ timeZoneId: "GTB Standard Time", dailyStartTimes: ["09:00", "17:00"], maxCyclesPerDay: 2 }`.

After independently reviewing and verifying all retained changes, any possible orphan process, config, credentials and HQ delivery, enable the task and explicitly resume in a hidden process. Do this only after the active coordinator finishes, to avoid conflicting work. If no slot is available, resume only arms the next eligible slot:

```powershell
$runner=(Resolve-Path .agents/product-studio/runner.ps1).Path
Enable-ScheduledTask -TaskName 'KeepItUp Product Studio'
Start-Process powershell.exe -WindowStyle Hidden -ArgumentList ('-NoProfile -NonInteractive -WindowStyle Hidden -File "'+$runner+'" -Resume')
```

Inspect `.agents/product-studio/runtime/status.json` for local truth: `running` needs a fresh heartbeat (under 60 seconds); `completed` records the last verified cycle; `scheduled_wait` means no model was invoked and the next slot is armed; `fault` and `paused` require deliberate resume; `owner_blocked` monitors scoped HQ responses. `lastStartedAt`, `lastSucceededAt`, `lastFailedAt`, `nextEligibleAt`, `dailyStarts` and `dailyLimit` separate work history from scheduling. `scheduleEnabled` is a timestamped OS-task observation, not a heartbeat. Unknown historical success times stay absent. Ignore `checkedAt` as activity evidence. Run stdout/stderr and result remain private in ignored runtime. `STUDIO_SOURCE_ROOT` lets the reporting helper access protected credentials without copying them. After a clean successful cycle, the supervisor validates the fresh report against Git HEAD, then atomically mirrors only `apps/web/public/standup/latest.json` to main. Preserve that authorized reporting change during integration.

Status persistence uses a same-directory [MoveFileEx](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw) rename with `REPLACE_EXISTING | WRITE_THROUGH`, writing a complete UTF-8 temporary file before changing the destination name. It never deletes the destination first and no longer uses `File.Replace`/ReplaceFile metadata-merging semantics. This addresses the confirmed `20260913T221328Z` failure: private diagnostics identify File.Replace at script line 51 with HRESULT `-2147023721`, Win32 `1175` (`ERROR_UNABLE_TO_REMOVE_REPLACED`), during independent verification.

Windows readers can briefly deny deletion. Writes retry sharing/lock violations for at most two seconds. `MoveFileEx` also reports busy files as access-denied even when the lock disappears before inspection, so a readable, non-read-only destination qualifies for the same bounded retry. Read-only/unreadable destinations fail; persistent access failure still faults after the bound, without changing any ACL. Tests hold a deny-delete reader through a write, then stress 100 replacements against 200 concurrent reads; readable snapshots remain valid JSON. Readers may themselves briefly encounter a sharing violation and should retry that read, never interpret it as an empty status. Supervisor failures retain only exception type, HResult, native error code, script line and timestamp in ignored `runtime/last-failure.json` and status; exception messages/provider text/stacks are excluded. Earlier interrupted work remains preserved and requires review; these fixes do not retroactively mark failed cycles successful.

Pause future triggers with `Disable-ScheduledTask -TaskName 'KeepItUp Product Studio'`. This does not interrupt an existing coherent cycle. After that cycle exits, `powershell -NoProfile -File .agents/product-studio/runner.ps1 -Pause` persists the pause. To resume, first inspect/fix the isolated tree and failure, enable the schedule and run the hidden `-Resume` command. Never remove locks, reset branches or delete unfinished work to make a failure disappear.

To update the isolated branch with newly approved main changes, pause and wait for the lock owner to finish, inspect both trees, and merge/review manually. Do not silently reset it. Local commits need independent integration review and separate production authorization.

Validation: authenticated read-only CLI smoke returned `RUNTIME_SMOKE_OK` on 2026-09-14 (existing ChatGPT session; no tool use, no project changes). Runtime unit checks cover latching, dirty-tree/failure/publication boundaries, atomic status replacement, exclusive locking/recovery, and PowerShell syntax. A successful smoke is not evidence that a mutating scheduled cycle or remote HQ reporting works; verify the first actual cycle before claiming continuous operation.

## Owner decision emails

September 14 steering: the personal-sender OAuth setup is paused while the support sending identity is clarified. Mail access is not a prerequisite for independent product work. The current source operating contract and experience queue govern future cycles.

Owner-authorized alerts can supplement HQ. Automatic email monitoring is disabled unless ignored runtime config explicitly contains the boolean `decisionEmailEnabled: true`; installation defaults to false. The current twice-daily setup does not enable it. When enabled within the existing owner-alert authorization, the supervisor runs `decision-email.mjs monitor` at scheduler checks and after verified cycles. It reads live HQ and authenticated decisions, queues only unresolved cards, and deduplicates exact content using private receipts. Report timestamp changes do not resend an alert. `runtime/decision-email-status.json` distinguishes missing provider, queued, confirmed send and uncertain delivery; an outbox is never evidence of sending.

Configure the selected recipient/sender privately in ignored `.env.studio.local` as `STUDIO_OWNER_EMAIL` and `STUDIO_OWNER_EMAIL_FROM`. Local Gmail delivery additionally requires `EMAIL_DELIVERY_ENABLED=true`, `EMAIL_DELIVERY_PROVIDER=gmail`, `GMAIL_CLIENT_ID`, `GMAIL_CLIENT_SECRET`, `GMAIL_REFRESH_TOKEN`, and `GMAIL_SENDER_EMAIL` equal to the selected sender. This uses Gmail send-only OAuth through fixed Google endpoints. No credentials or personal addresses belong in committed files or public HQ. The chat Gmail connector is separate from local runtime access.

After a real interactive connector send of the exact current queued digest, record its provider ID with `node .agents/product-studio/decision-email.mjs record-receipt . <message-id>`. Never record a draft or a different digest as sent. If a send times out after dispatch begins, automatic resend is suppressed; reconcile the provider receipt privately before clearing that exact uncertain entry. Routine model cycles must not send their own duplicates. The owner authorization covers decision alerts only, not recruitment or other account messaging.

## Newer HQ report during verification

When a coordinator publishes a newer valid source snapshot while a cycle is being verified, the supervisor preserves that snapshot. It still verifies the older cycle artifact against its clean commit, then records `reportSuperseded=true`, `localReportVerified=false`, and no live-publication claim unless independently matched. This normal concurrency case no longer stops the worker. Invalid, future-dated, dirty or uncommitted reports still fail verification.
