# UX evaluation — 14 September 2026

## Assessment

KeepItUp has a distinctive, credible core: meet adults by joining a small sports event, with host approval before private coordination. The source already contains thoughtful cancellation, blocked access, reporting, approximate location and post-event reflection behavior. The largest design opportunity is to let a newcomer experience that core before asking them to construct a profile.

This is a source-based heuristic evaluation, not a measured conversion study or a completed browser accessibility audit. Read the root working agreement, product-studio skill and experience principles, vision, roadmap and agent state. Inspected landing, signup, discovery, event detail, request controls and accepted room. Historical agent-state entries include contradictory eras; current source is the evidence for observations below.

## Recommended concept: “Pick a plan. Meet through play.”

Keep the existing product name. Treat this as a reversible experience direction, not a final brand, pricing or launch geography decision.

First-screen definition: **“Meet people through local sports.”** Supporting copy: “Find a small game, ask the host for a place, and meet in real life. For dating, friendship or a new group.” Adults 18+ remains visible. The main action takes visitors to registration with an honest label such as “Create a free profile”; a second action invites them to “Try an example”.

The demonstration is a tactile invitation rather than a dashboard. Three real buttons choose an example: easy run, friendly padel, relaxed chess. Selecting one immediately changes the activity illustration and a short invitation containing skill level, duration and approximate area. Clearly label the object “Example invitation — not a live event”. Example selection stays in local component state and is never recorded as a relationship preference.

The invitation teaches three deliberate states:

1. **Choose a game.** Show the essentials and an “Example request” button. Display “Meeting point shared after acceptance”.
2. **Ask the host.** Explain that real requests wait for a host decision. Offer “See an accepted example” and “Back”; never auto-accept or suggest a guaranteed place.
3. **Meet and play.** Show an illustrative room checklist: meeting details, group coordination and an easy way to cancel. Use a generic “Meeting point shared” placeholder, never real precise coordinates or participant identities. End with registration or authenticated discovery.

This is fun because the choice changes a tangible plan and reveals a useful outcome. It needs neither a score nor an extended game loop. A small ball movement on sport selection can add personality; reduced-motion users get the same immediate state change.

## Build-ready behavior and states

- Layout: on small screens, definition and primary action precede the interactive invitation; on wider screens, text and invitation sit side by side. No horizontal scroll at 320 CSS pixels. No fixed element may cover the CTA or keyboard focus.
- Controls: native buttons, visible text labels, selected state through `aria-pressed`, a visible focus ring and at least 44 CSS-pixel targets. State changes announce one concise status. Do not move focus away from a button unnecessarily.
- Motion: short transitions only; respect `prefers-reduced-motion`. No auto-playing progression, countdown, drag-only action or sound.
- Initial/JS-unavailable: server-render the product definition and a fully understandable labelled example. Registration and how-it-works links continue working.
- Reset: switching sport resets a simulated request. “Try another example” returns to the first state. No storage, backend mutation or misleading “request sent” toast.
- Real-app boundaries: this demo never reveals accepted room data, creates a request, sends a message or bypasses authentication. A real accepted event remains authorized by existing backend checks.
- Recovery: real discovery must distinguish no nearby supply from filters producing zero matches; real requests retain pending, accepted, declined, full, cancelled and failure states. Do not put cheerful animation over an error or rejection.

## Full journey after the concept

The concept should eventually carry into an activity-first signup, compact discovery, invitation detail and accepted event room. The room should prioritize time, meeting point, latest change and coordination, with leaving/reporting always findable. Reflection stays optional and private, with no public rank or pressure to approve another person. Existing event-room, request recovery and reflection controls are assets to preserve, not replace wholesale.

## Verification and product learning

For the first implementation slice, verify desktop/mobile layout, keyboard-only completion, visible focus, reduced-motion behavior, semantic announcements, truthful sample labelling, no sensitive state persistence and no mutation/API call from the demo. Run relevant component tests, type checks and the existing landing tests. A source review alone does not establish these visual/accessibility results.

Proposed comprehension test, not a measured result: show the first screen to five unfamiliar adults, then ask “What is this?”, “What would you do next?” and “When would you see the meeting point?” Target at least four of five independently describing a local sports meetup with a host request, and zero mistaking the examples for available places. Observe whether they expect dating, friendship and group participation to have equal standing.

Track only coarse approved funnel events if implemented; do not log sport choices, intent, location, request text or member identifiers for this demonstration. Evaluate successful comprehension and progression toward a real event, not repeated demo plays or dwell time. Interview recruitment or outreach remains an owner-authorized external action.
